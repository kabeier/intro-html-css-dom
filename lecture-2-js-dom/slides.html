The browser turns HTML into a tree of objects: the DOM

  • document
    • html
      • head …
      • body
        • header (h1 id="page-title")
        • main
          • section id="team"
            • ol → li "Pikachu"
  • Every element becomes an object
  • Text inside is a text node
  • Attributes (id, class) live on their element
  • Change the object → the page changes, no reload

DOM = Document Object Model: the page as objects JavaScript can change.

The plan: How the browser turns our HTML into a tree of objects called the DOM. That tree is what JavaScript changes.

HTMLCollection vs NodeList: neither is an array

HTMLCollectionNodeList
FromgetElementsBy…querySelectorAll
Page changesupdates: livestays: a snapshot
[0] .lengthyesyes
for...ofyesyes
.forEachnoyes
.map .filternono
const cards = document.querySelectorAll(".card")
const boxes = document.getElementsByClassName("card")

// NodeList: forEach works
cards.forEach((card) => console.log(card.id))

// Both: for...of works
for (const box of boxes) {
  console.log(box.id)
}

// Need map? Make a real array first
const ids = Array.from(cards).map((card) => card.id)

Use for...of on either. For .map or .filter: Array.from(list) first.

The plan: Why a list of elements isn't an array: HTMLCollection vs NodeList, and how to loop over each one.

About 2 minutes. Say: "Last slide's console said NodeList. It looks like an array, but it isn't one. There are two of these list types, and they don't do the same things."

Point atHow it works
From rowThe method decides the type. getElementsByClassName and getElementsByTagName give an HTMLCollection (so does .children). querySelectorAll gives a NodeList.
Page changes rowLive = the list updates itself. Add a card with JavaScript and an HTMLCollection grows from 3 to 4. A NodeList from querySelectorAll is a snapshot of that moment: it stays at 3.
.forEach rowOnly NodeList has it. On the other: boxes.forEach is not a function.
.map rowNeither has it: cards.map is not a function. People often think NodeList has map because it has forEach. map and filter are array methods.
Array.from(cards)Copies the list into a real array, so every array method works. [...cards] does the same. The result is a normal array: it never updates.
OutputOn our page each loop prints about, team, contact. ids is ["about", "team", "contact"].

If someone asks about the live trap: loop over an HTMLCollection by index and remove the class as you go, and items get skipped, because the list shrinks under you. With 3 cards, one is left with its class. Looping over a NodeList has no such problem.

Say: "We use querySelectorAll almost everywhere, because the snapshot does what you expect."

Two "stop" methods, two different jobs

MethodStopsExample
evt.preventDefault()the browser's defaulta form reloading the page; a link navigating
evt.stopPropagation()the event reaching parent elementsa click on a list item also counting as a click on the card

preventDefault = "browser, don't". stopPropagation = "parents, don't hear this".

The plan: Two stop methods with two different jobs: preventDefault and stopPropagation.

Curriculum example: keydown + evt.code === "Space" + preventDefault stops the page scrolling. (Our deck uses Space for "next slide": same idea.)

A click bubbles up through every parent

li "Pikachu" ← you click here
ol (listener: remove the li)
section#team (listener: toggle the outline)
body → html → document
  • The event starts at the target
  • Then it visits each parent, bottom to top
  • Every listener on the way runs
  • stopPropagation() ends the trip

One listener on the list can handle every item, even new ones (event delegation).

The plan: How one click travels up through every parent element: bubbling.

Say: "Clicking the li is also clicking the ol, the section, the body. Every listener on the way hears it."
